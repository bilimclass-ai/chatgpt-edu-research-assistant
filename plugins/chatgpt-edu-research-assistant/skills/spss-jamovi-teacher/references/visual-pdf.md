# Visual PDF teaching companion

Create a genuine downloadable PDF for substantive SPSS/jamovi teaching requests after onboarding. This is additional to the short chat response and any required Excel practice file. Use the selected language only; produce three language versions only when requested. These are original presentation rules, not instructions from the source books.

## Choose the visual that teaches the idea

| Learner's task | Useful visual | What to explain |
|---|---|---|
| Describe data | A small labelled table and dot plot or histogram | One row/one person; typical value and variation |
| Compare independent groups | Two groups of individual points with clearly labelled summaries | Different people in each group; difference and spread |
| Compare before/after | Paired points joined by lines | Each line is one person; changes differ between people |
| Understand correlation | Scatterplot with plain axis labels | Each point is one person; direction does not establish causation |
| Clean or score data | Original value → transformation → new value | Show a real zero, a missing value and a reversed item when relevant |
| Read output | A few relevant rows with numbered callouts | Which number answers the question and what it means |
| Resolve an error | Expected state beside the observed issue, if supplied | One likely cause, the repair, and what should change |

For another method choose a similarly small, relevant illustration. A visual must clarify a decision or relationship, not merely decorate the page. Do not invent results to fill a chart. Use inspected user data, a checked bundled example or explicitly labelled synthetic values. If only the concept is known, draw a labelled conceptual diagram with no fabricated inferential statistics.

## Short document structure

Usually use 2–4 A4 portrait pages; one page is enough for a small question. Extend only when the requested material needs it. Avoid a separate decorative cover.

1. **What are we trying to learn?** State the question in ordinary language, define the relevant columns, and use one clear example visual. Explain its message in two or three sentences before naming technical terms.
2. **What do I do in the program?** Give a few numbered actions, matching variable names to their destination fields. Pair actions with their purpose and expected screen state. For a concept-only question, use this space for another explanatory example instead of irrelevant software steps.
3. **How do I read the result?** Highlight only necessary values, explain them in everyday language, give one justified conclusion and one relevant limitation. Include a tiny practice check when useful. For troubleshooting, show how to check that the repair worked.

These are content roles, not mandatory page breaks. Keep a figure, its caption and its explanation together. Include software/version when known, data provenance, page numbers and a few relevant clickable sources. Identify whether numbers were computed independently or obtained from actual native output.

## Honest interface illustrations

Use real inspected screenshots when available, cropped to the relevant area with readable numbered callouts. Do not require a screenshot to teach. If none is available, use a simple flow diagram or a clearly labelled schematic of variable placement; it must not masquerade as the application's actual interface. Label it in the learner's language: “Сызбалық түсіндірме; нақты скриншот емес” / “Схема, не снимок экрана” / “Schematic, not a screenshot”. Verify menu wording where version-sensitive. Never fabricate native screenshots or place invented numbers inside a supposed software output.

## Legibility and verification

Use available PDF authoring tools and follow the applicable PDF skill, including its rendering workflow. Prefer text and vector diagrams; no image generation or network search is needed for a simple schematic. Use an embedded font supporting Kazakh, Cyrillic and Latin, normally 11–12 pt body text and larger headings. Test characters such as Ә Ғ Қ Ң Ө Ұ Ү Һ І. Keep labels readable, provide whitespace and strong contrast, and distinguish groups with labels/shapes as well as color. Explain axes and units; avoid misleading scales and 3D charts.

Reopen the PDF, check extracted text and page count, then render every page and inspect for clipping, missing glyphs, overlapping labels and tiny screenshots. Reconcile data, n, means, differences and any other reported statistics with the same Excel file or checked key. A valid PDF file alone is not proof of readability. Repair defects before delivery. Never claim inspection if rendering was unavailable; state the specific limitation.

## Efficient delivery

Reuse existing data and checked calculations. Load only the sources needed for the current topic. Keep the chat to the main idea, the PDF attachment and one next action; do not paste the document in full. Use the file-delivery convention of the available PDF tooling. Reuse an unchanged companion for follow-up questions; revise only when the content changes and ensure the delivered file is the checked revision. If PDF creation fails, explain the limit and provide an accessible inline explanation, without claiming a PDF exists.
